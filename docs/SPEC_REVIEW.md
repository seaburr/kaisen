# Kaisen v0 spec: skeptic review

Reviewed 2026-10-29 against `docs/SPEC.md`, the PicoPaaS docs and code (`docs/USER_GUIDE.md`, `docs/API.md`, `app/config.py`, `app/resources.py`, `app/k8s_manifests.py`) and the concept and assessment docs. "Verified" means I found the evidence cited. "External" means GitHub or Anthropic behaviour I could not check from this repo and that Chas or the builder must confirm.

## 0. Verdicts

| Milestone | Verdict |
|---|---|
| M0 | GO WITH CHANGES (meter first, fix required changes 1, 4, 5, 7 and 13 in section 6 before building) |
| M1 | NO-GO as written. The gate design is bypassable (required changes 1 to 3), the budget is inconsistent (change 4) and the CI wait model contradicts the wall clock (change 6). GO after those are fixed. |
| M2 | NO-GO. The self-enhancement loop is unmeasurable as designed (change 11) and the kit can weaken the reviewer (change 9). Defer until M1 produced real metered data. |
| M3 | NO-GO. Pure speculation on M1/M2 outcomes; there is no acceptance test. Re-spec after M2. |

## 1. Claims that are false, misapplied or unverified

1. FALSE (misapplied constant): "5 apps x 200m against `NODE_CPU_CAP_M` 1500" (SPEC 2, risk 7). `app/config.py:174-178` says that constant is "what ONE worker node can schedule for a single app", i.e. the ceiling for an admin per-app override, not a sum-of-apps budget. Real headroom is node CPU/memory requests (64m/128Mi each, `config.py:168-172`) against the actual node pool, which this spec never checks. Ask sre for current node requests before claiming 5 apps fit.
2. FALSE: "rollback via the versions API" (SPEC 8). There is no versions API. The real surface is `GET /apps/{id}/image-history` (last 5 digests that reached running) and `POST /apps/{id}/rollback {digest}` (`docs/API.md:194-195`). Also the platform already auto-rolls back a never-healthy image ("event `rollback`", API.md:195), so the orchestrator's "failed prod health check triggers rollback" duplicates and may race it. A rollback also stops auto-update for that tag (USER_GUIDE 455-456).
3. FALSE or at least understated: app-limit fix. SPEC 2 and 16 say "dedicated user, limit raised to 5". Verified: a normal user is capped at `MAX_APPS_PER_USER`=5 (`config.py:133`, `resources.py:25-26`), signup is approval-gated, and API keys can only be minted in a browser session (`API.md:133,138`). So the dedicated account needs: an approved signup, an admin to raise `app_limit` to 5, and Chas logging in as that user in a browser to mint a full key. With exactly 5 slots (orchestrator + 2 prod + 2 previews) there is zero room for the third goal, a second preview, or a crashed leftover preview. A stuck delete or leaked preview blocks the pipeline (403 at limit, API.md:253). Alternatives: put Kaisen on an admin account (limit up to 10, `config.py:138-139`), which breaks the "dedicated user" blast-radius story, or accept one preview slot total.
4. UNVERIFIED and likely wrong: "GitHub Actions is free for public repos" implies the workspace repo is public. The spec never says public or private. Private-repo free minutes are limited (External; check Chas's plan). The CI design (up to 12 rounds per issue, Playwright, docker builds) can burn a private quota in days. If the repo is public, see 4.1 (anyone can file issues and comments).
5. UNVERIFIED: "PicoPaaS Postgres ... DATABASE_URL". Verified facts the spec omits: the PG role has `CONNECTION LIMIT 5` (USER_GUIDE 300, 613), TLS is required and CA-verified (`sslmode=verify-full` with `${{ db.ca_cert }}`, USER_GUIDE 231, 289-297), and the URL scheme is `postgres://` which SQLAlchemy 2 rejects unless rewritten to `postgresql+psycopg://`. Spec says SQLAlchemy plus APScheduler with default pooling; the default pool (5) plus scheduler thread plus request threads exceeds 5 and fails with "too many connections for role". Writes also go read-only at 50 MB (USER_GUIDE 488); prune jobs must DELETE rather than INSERT first.
6. UNVERIFIED: "backed up when backups are on". Whether new apps start with backups on is a platform setting (USER_GUIDE 387). Check before relying on it for the audit DB.
7. CORRECT but not what the review request assumed: egress. The platform does NOT allowlist hosts. Verified: all TCP except SMTP, private ranges blocked (USER_GUIDE 527-536). The allowlist to Anthropic/GitHub/registries exists only in the concept doc's future runner tier. The spec states this correctly (SPEC 11) and relies on an in-code host allowlist, which is a convention, not a boundary. Do not describe it as enforced.
8. CORRECT: images must be public (422 otherwise, USER_GUIDE 35, API.md:227), non-root, 512 MB compressed layers; API keys are not per-app; a full key is needed for writes (API.md:63). CPU is 200m default (`config.py:170`), RAM 384Mi, scratch 250 MB (`config.py:179`), apps get one replica.
9. MISSING FACT: ports must be 1024 to 65535 (API.md:243), the named-USER-is-UID-10001 file-ownership trap (USER_GUIDE 33), outbound bandwidth 20 Mbit/s (USER_GUIDE 37; fine for the orchestrator, and for a game). Generated Dockerfiles in the kit must encode these (nginx-unprivileged on 8080, numeric USER). Absent from the spec.
10. UNVERIFIED (External): "GitHub Packages are private by default on first push" and there is no API to flip visibility. I believe both are true; Chas must confirm on the first push. Three packages (`kaisen`, `-checklist`, `-invaders`) means three manual UI flips, each blocking the first preview deploy (422 from `/apps/spec`).
11. CONTRADICTION: Anthropic console limit. SPEC 6 says set it to "daily cap x 2" ($20); SPEC 16 says "suggest $10/day". At $10 the outer cap equals the inner cap, so it provides no margin and trips mid-run.
12. UNVERIFIED: prompt caching plus "older tool results are truncated" (SPEC 3, item 3). Rewriting earlier messages changes the prefix and invalidates the cache from that point; truncating each turn defeats the cost saving the same paragraph claims. Cache TTL (External, default 5 minutes) also expires during any `get_ci_result` wait over 5 minutes.
13. UNVERIFIED: ~40 MB SDK, ~120 MB app RSS, ~150 MB image. Plausible, none measured. M0 acceptance covers RSS and image size, which is the right place.

## 2. Feasibility inside PicoPaaS caps

- Orchestrator process fits 384 MB / 200m if it never runs tests, never installs npm. The no-shell decision is correct. No change.
- Rolling update overlap: non-volume apps use `RollingUpdate maxSurge 1, maxUnavailable 0` (`k8s_manifests.py:608-611`). Every deploy of Kaisen runs two pods at once for the readiness window. Two schedulers means two runs on the same issue, double spend and double pushes. The spec relies on "single replica, single worker". It needs a Postgres advisory lock or a DB lease row, with fencing (check lease before every model call and push). The MySQL GET_LOCK trick PicoPaaS uses (CLAUDE.md) has no equivalent mentioned for the spec's PG. Also, `healthCheck` enabled adds a liveness probe that restarts the container after 3 failures of 5 s timeout (USER_GUIDE 425-430): a long synchronous blocking call (clone, gitleaks, CI wait) on the event loop will fail `/healthz` and kill a run. Run the loop in a thread and keep `/healthz` independent.
- Build location: all execution is GitHub Actions. That is the right call, but it is also the cost driver (section 3 and change 6). The spec never says who builds the Kaisen image itself. It lives in a different repo (`~/source/kaisen`) than the workspace repo, so that repo needs its own workflow, GHCR permission and package flip, and its own deploy path (first manual `picopaas apply`, then redeploy by Chas). Not listed in section 16.
- Smoke test ordering: gate 4 is "Playwright smoke against the preview URL", but the preview is deployed by the orchestrator after CI builds the image. A required check inside the same workflow run cannot depend on a deploy that happens after the workflow. Either the orchestrator posts a commit status after running the smoke itself (it has no browser; 384 MB makes Chromium infeasible), or the workflow must call back to the PicoPaaS API itself (that requires `PICOPAAS_API_KEY` in GitHub secrets, which the spec says agents never touch and which is reachable from any workflow edit, see 4.2). The cleaner design: CI runs the smoke against the container started inside the Actions job (`docker run` + Playwright), and the preview deploy is for human viewing only. Pick one; the spec currently has an unsatisfiable gate.
- Hostnames: generated per app (USER_GUIDE 4, 163), so the orchestrator must read `hostname` from the `App` response. Fine, but the "name" the spec assigns (`kaisen-<slug>-preview`) is display only, 1 to 255 characters (USER_GUIDE 163). No DNS-length problem.
- App count and create/delete churn: the orchestrator must handle 403 at limit, and delete previews in a finally block even when a run dies. The boot-time orphan sweep (risk 6) only resets issue labels, not leaked preview apps. Add "list apps, delete any `kaisen-*-preview` not owned by an active run".
- Image tag mutability: SHA tags are right; with `auto_update` default on for a mutable tag it would redeploy unexpectedly, so SHA tags need no further action. Keep it.

## 3. Cost realism

No metered baseline exists anywhere (concept doc says so). Sketch with explicit assumptions (Sonnet-class list pricing ~$3 in / $15 out per million, cached read ~0.1x; confirm in `config.py` price table at M0):

- One builder turn: ~40k input mostly cache read ($0.012) + ~5k fresh input ($0.015) + ~1.5k output ($0.023) = ~$0.05. 40 turns = ~$2. That is already two thirds of the $3 `KAISEN_RUN_USD_CAP` for a single role, with no cache invalidation from truncation (claim 12 above makes this 2x to 4x worse).
- One issue touches builder + verifier + security-reviewer, and docs sometimes: realistic $4 to $8 per issue with CI re-reads. Checklist app with 8 to 12 issues plus planner: $35 to $90. That exceeds the stated M1 estimate ($15-30) and the default project budget ($25), and the daily cap ($10) stretches M1 over 4 to 9 days. M2 ($30-70) plus kit-improver plus two fixture runs is another 5 to 10 days at $10/day.
- The concept doc's own pass bar for a whole real app is <= $50, fail > $150. Two toy apps estimated at $45-100 is outside the "toy" regime; this suggests the issue breakdown is too fine or the loop too chatty. The planner should be told to produce <= 5 issues for the checklist and <= 8 for the game.
- Nothing in the spec accounts for ask_human restarts (the run ends, so the next run re-reads everything), CI log tails, or the cache-TTL cliff.

Proposed hard budget (replace SPEC 6 defaults):

| Scope | Cap |
|---|---|
| Run | $2 (planner/verifier/security-reviewer $1) |
| Day | $8 (and Anthropic console limit $16, 2x) |
| Checklist project | $30 |
| Invaders project | $40 |
| Self-enhancement total for v0 | $10 |
| Whole v0 | $100, then a human re-approves |

Metered-first M0 (new acceptance, replaces "ping run"): run three fixed micro-tasks against the real model with the exact tool loop: (a) read-only summarise a 200-line repo, (b) write one file plus one CI round trip, (c) ask_human + resume. Record tokens by kind (fresh, cache write, cache read, output), turn counts and wall-clock for each. Publish a measured cost table and a projected M1 cost from it. Gate M1 on projected M1 <= 70% of the checklist budget, else shrink scope. Reconciliation with the Anthropic console must be to the cent per batch, not "within 5%", because 5% hides a missing cache-write line item.

## 4. Security

4.1 Public repo and untrusted principals. If the workspace repo is public (the free Actions assumption), anyone can open issues, comment, and PR from forks. The queue is "issues, PRs and labels" and the answer path is "answering by comment on GitHub ... orchestrator polls those comments" (SPEC 10). Nothing says the orchestrator checks the commenter's login. A stranger who comments "approved" on a `human` issue approves a prod deploy or a budget raise. Required: allowlist the GitHub login (compare `user.login` and `author_association` == OWNER) on every consumed issue, comment, label and review; ignore everything else; and make any state label change by anyone other than the bot or Chas a no-op or an alarm (labels need triage permission, so only collaborators, but the PAT itself is a collaborator).
4.2 Workflow files are the weakest link. The PAT has Workflows RW (SPEC 7, 16) and the CI jobs are the only enforcer of gates 1 to 4. A branch workflow file runs from the PR branch: a PR that edits `ci.yml` so the required job "test" always passes defeats gates 1-4 and merges if only required status checks protect `main`. The spec's mitigation is a code path check ("builders cannot touch `.github/workflows`"), which protects against the model, not against a compromised orchestrator process, a bug, or a path-normalisation bypass (`projects/x/../../.github/workflows`, symlinks, case folding). Required: (a) protect `.github/**` and `CODEOWNERS` with a ruleset requiring review by a code owner who is not the PR author; (b) reject any diff touching `.github/` in the scm step in code (not just the write tool); (c) pin workflow permissions to `contents: read` at the top level and grant `packages: write` only in the build job triggered on `push` to `main`, never on `pull_request`.
4.3 The review gate cannot be what the spec says. Gate 5 and the "security-reviewer verdict recorded as a PR review" both fail on GitHub's rules: PRs opened with Chas's PAT are authored by Chas, and a review by the same account cannot approve (External; GitHub forbids self-approval). Check runs can only be created by a GitHub App, not a PAT. So the verdict has to be a commit status context, and "Branch protection ... no direct push" is also bypassable: if the PAT's owner is the repo owner/admin, merges via API can bypass protection unless the ruleset has no bypass actors and "include administrators" is on (External). The spec says "the token has no admin scope so it cannot change this", but not changing settings is different from not being exempt. Fix: use a second identity (machine user, or a GitHub App, which the concept doc already prescribes for the product) so Chas is a different human reviewer, and verify with a negative test that a PAT-driven merge of a red PR fails.
4.4 Builder write scope. SPEC 11: "writes confined to `projects/<slug>/` and `kit/`". Builders must not write `kit/`; if they can, a builder PR editing `kit/roles/security-reviewer.md` merges on green with no approval (only `kit/protected/` is gated). Role-specific path scopes: builder = `projects/<slug>/` only; kit-improver = `kit/` minus protected; nobody = `.github/`, `brief.yaml`, `fixtures/`. Enforce server-side at `commit_and_push` against the final staged diff via `git diff --name-only` after normalisation, not on `write_file` arguments.
4.5 Self-modification surface. Protected list is gate definitions, budget rules, security policy, loop rules. Not protected: the security-reviewer's own prompt, the verifier's prompt, the `<untrusted>` wrapper text, the tool descriptions. A kit-improver PR that dilutes the reviewer prompt looks like prompt tuning, passes a fixture that does not test security, and is merged by a human skimming 40 lines. Also: "<= 40 changed lines" is trivially evaded by one very long line or by adding files. Mitigation: move all `kit/roles/*-review*` and the untrusted-wrapping text under protected; size limit by bytes and files (e.g. 3 files, 4 KB); the fixture suite must include seeded vulnerable PRs the reviewer must block (a regression test for the security gate itself, run on every kit PR).
4.6 The friction channel is an injection channel. `friction` signatures are derived from CI logs, issue text and dependency output, all untrusted, and fed to the kit-improver as "evidence". A malicious dependency can print text that becomes the improver's input. Treat evidence as data: only normalised signature strings and numeric counters from the DB reach the improver; no raw log text.
4.7 Token blast radius, restated honestly. GitHub PAT: Contents RW + Workflows RW + PRs RW on one repo means junk branches, branch deletion (including `main` if the ruleset lacks deletion protection), force-push to non-protected branches, rewriting workflow files on a branch (and 4.2). PicoPaaS full key: can create, update, delete, and read the logs and env of every app on that account, including the secrets the orchestrator itself holds (`Kaisen` app env: ANTHROPIC key is stored Fernet-encrypted, not shown to API with the secrets list, but `PICOPAAS_API_KEY` can redeploy Kaisen with a different image or spec). That is: the orchestrator's key can replace the orchestrator. A compromised orchestrator or a malicious generated app is therefore not contained by the dedicated-account idea; it is contained only by a dedicated account that holds nothing else. Keep that rule explicit in section 16 and test it (no other apps on the account, ever).
4.8 Generated apps are hostile code running next to the key. The generated apps are separate pods with `app-*` namespaces, no cross-app traffic (USER_GUIDE 520), but they run with full internet egress, so a generated app can exfiltrate anything it is given. v0 gives them no secrets: good, keep it as a hard rule, not a default.
4.9 Prompt injection specifics. The `<untrusted>` wrapper is a request, not a control; the real controls are tool scope and gates, so the rest of the list matters more: (a) `get_ci_result` returns attacker-influenced log tails; cap length and strip control characters; (b) `ask_human` text and issue titles are rendered in the inbox UI, so escape them (stored XSS in an admin session cookie that can raise caps); (c) the inbox must be CSRF-protected, cookie `HttpOnly; Secure; SameSite=Strict`, with login rate limiting. `KAISEN_ADMIN_PASSWORD` as a single shared password on a public hostname needs lockout; PicoPaaS's own rate limiter is not inherited.
4.10 What a malicious issue or PR could do today under this design: a comment from a stranger (4.1) approving a deploy; an issue text steering the builder to add an exfiltrating dependency (the dependency review is also an LLM reading attacker-written README text); a PR to `.github/workflows` that always-green merges (4.2); a Dockerfile `RUN` that bakes network access (harmless to Kaisen, but it runs in Actions with the workflow token and in the preview pod); a branch pushed to `kit/` that changes the reviewer. None are prevented by the `<untrusted>` tags.

## 5. Omitted by the spec

- Who is allowed to author work (4.1), and a negative test for it.
- Lease/fencing for the single run (section 2).
- Behaviour on a deploy of Kaisen itself mid-run: the 30 s grace window and `ask_human` continuity (the run is "ended", state lives only in GitHub labels and a truncated transcript).
- A time zone and clock for the daily cap (UTC day vs `brief.yaml` timezone; where is the cap reset?).
- A real definition of "taste review" (M1 acceptance mentions "1 taste review" without defining what it is or who does it).
- Rate limits on the GitHub API (5000/hour per PAT, secondary rate limits for content creation) and the Anthropic API (tokens per minute at the key's tier; a fresh key may be in a low tier and 429 the builder loop). Retry/backoff and 429 accounting are not specified, and a retry storm costs real money.
- Anthropic usage terms for an agent loop on a standard API key: fine on a metered key per the concept doc's "BYO API keys only"; confirm no org-level policy applies. Not needed for v0 since the key is Chas's.
- Cleanup: deletion of failed preview apps, stale branches, GHCR old versions (storage limits on GHCR for private packages, External).
- DB schema migrations for Kaisen itself (Alembic or equivalent) and the DB-full policy at 50 MB: transcripts, events and the digest need a pruning job defined as a gate, not a risk bullet.
- How the Kaisen image is built and who deploys updates to Kaisen (section 2).
- A restore drill for the audit DB.
- Reproducibility: `KAISEN_MODEL` unpinned model alias drift changes behaviour between M1 and M2 runs; pin the model ID and record it in each event.
- Time budget: wall-clock per issue including CI queue time; GitHub-hosted runner queue delays are not modelled.
- The third goal's DB and volume conflict with the "no DB, no volume" generator defaults; fine for v0 but then the M3 acceptance has to say what it tests.

## 6. Required spec changes, ordered by severity

1. Fix the review and merge gate design (4.3 plus 4.2): second GitHub identity (machine user or App) so Chas can be a required code-owner reviewer; ruleset with no bypass actors; reviewer verdict as a commit status, not a PR review; protect `.github/**`, `CODEOWNERS`, `brief.yaml` with code-owner review; negative tests that prove a red PR and a workflow-editing PR cannot merge via the PAT.
2. Define identity and untrusted-principal handling (4.1): every issue, comment, label, review and PR consumed by the orchestrator must come from an allowlisted login; strangers are ignored; decide public vs private repo explicitly and cost it (Actions minutes if private, exposure if public).
3. Resolve the contradictory CI model (section 2 and change 6): remove the "smoke against the preview URL" gate or make it run inside Actions against the locally started container; pick one and state which job is the required check.
4. Recompute the budget and daily cap (section 3): replace the $15-30/$30-70 estimates with measured M0 data; adopt the caps in the table; fix the console limit contradiction (6 vs 16); make M0 a metered experiment with the three micro-tasks and cent-level reconciliation; drop "truncate older tool results" or replace it with a cache-aware summarisation at fixed checkpoints.
5. Add the lease and fencing for single-run guarantee (section 2), because every Kaisen deploy surges a second pod (`k8s_manifests.py:608-611`); run the agent loop off the request thread so the liveness probe cannot kill a run.
6. Reconcile wall clock with CI waits: 12 CI rounds at 3 to 5 minutes each is 36 to 60 minutes against a 30-minute run cap. Either split a run into resumable steps persisted per CI round (state machine, run ends while waiting, a webhook-less poll resumes it; also avoids the 5-minute cache TTL cliff) or lower the cap to 4 rounds. Recommend the split.
7. Postgres specifics (section 1.5): pool max <= 5 (use 3), `sslmode=verify-full` with `${{ db.ca_cert }}`, scheme rewrite, read-only at 50 MB handling, retention job. Move the DB schema from "tables" to an Alembic migration included in M0 acceptance.
8. Role-scoped write paths enforced on the staged diff (4.4); builders cannot write `kit/`; reject `.github/`, symlinks and `..`.
9. Narrow self-enhancement for v0 (4.5, 4.6 and change 11): protect reviewer/verifier prompts and the untrusted wrapper; evidence is signatures only; size limit by bytes and file count; a seeded-vulnerability regression set the reviewer must pass for any kit PR.
10. Make the app-slot plan honest (section 1.3): one preview slot, delete-in-finally plus an orphan sweep, an admin approval and `app_limit` raise as an explicit pre-M0 task, and a check of node headroom with sre rather than `NODE_CPU_CAP_M`.
11. Fixture A/B is statistically meaningless (n=1 versus n=1, nondeterministic model, $1.50 against a $2 to $3 typical run). Replace with: a deterministic offline check (kit lint + prompt regression on recorded transcripts, no model) as the gate, and one live fixture run as a smoke only, not a pass/fail on token counts.
12. Secure inbox and rendering (4.9): CSRF, cookie flags, login lockout, escaping of all untrusted strings, redaction applied to UI transcripts too.
13. Add the missing Chas prerequisites to section 16: build and first deploy of the Kaisen image (separate repo, workflow, package flip), approved signup of the dedicated PicoPaaS user, browser-minted full key, GitHub second identity, public-vs-private decision, three package flips.
14. Correct the false statements in section 1 (NODE_CPU_CAP_M, versions API, "console limit x2 vs $10", egress described as an enforced allowlist).
15. Pin the model ID and record it per event; add 429/backoff accounting on both APIs.

## 7. Minimal viable path that still delivers checklist app plus game

1. Pre-work (Chas, ~30 min): approve and raise the dedicated PicoPaaS user to 5 apps; second GitHub account or App; repo decision; ruleset with no bypass; `ANTHROPIC_API_KEY` with a $16/day console limit.
2. M0 (metered): skeleton + login + pause + PG lease + the three micro-task experiment. Exit: measured cost table, wall-clock table, GHCR flip rehearsed with a throwaway image, Kaisen self-deploy rehearsed.
3. M1-lite: planner (<= 5 issues), builder, security-reviewer, scm code, CI gates 1 to 3 plus the Playwright smoke inside Actions, a single preview slot, human approval on every prod deploy. Skip the verifier role, docs role, daily digest, GitHub-comment answer path (use the inbox only, so 4.1 has a single input surface) and `/metrics` extras. Checklist app live and under $30.
4. M2-lite: game via the same loop with a $40 cap. Self-enhancement reduced to a human-run report: Kaisen emits the friction table and a proposed kit diff as a draft issue, Chas applies it by hand. This preserves the no-self-merge rule while deferring the fixture machinery until there are measured runs worth tuning.
5. M3: write after M2, once the third goal and the real numbers are known.

This path removes about 40% of the spec (verifier, docs, digest, fixture runner, kit-improver automation, M3 plug-ins) and every item that blocked the verdicts.
